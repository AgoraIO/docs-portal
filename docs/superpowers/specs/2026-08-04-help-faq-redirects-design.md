# Help and FAQ legacy redirect cleanup

**Date:** 2026-08-04
**Status:** Approved in chat, awaiting written-spec review

## Problem

Some legacy Agora docs Help/FAQ URLs from the old site now return `404`, even
when the equivalent migrated FAQ page exists under `/en/api-reference/faq/...`.
The immediate example is:

- `https://docs.agora.io/en/help/integration-issues/system_volume` returns `404`
- `/en/api-reference/faq/integration/system_volume` exists and returns `200`

Local source content also still contains old `/help/...` links, so generated docs
can keep publishing references to legacy URLs that no longer resolve.

## Goal

Find all high-confidence broken legacy Help/FAQ links in the English docs scope
and add permanent redirects to their current FAQ pages. Also update local docs
content so source files link directly to current `/en/api-reference/faq/...`
paths.

## Scope

Included:

- Legacy Help/FAQ URLs that are clearly old docs content:
  - `/en/help/...`
  - `/help/...`
  - `/en/faq/...`
  - legacy product FAQ paths that map to current API Reference FAQ pages
- Targets under `/en/api-reference/faq/...`
- English docs content under `content/docs/en/**`
- Redirect source data and generated redirect artifacts

Excluded:

- Non-FAQ product docs redirects unless they are already required as evidence for
  a Help/FAQ migration.
- API reference source-page failures on `api-ref.agora.io`.
- Low-confidence semantic matches where no current FAQ page can be verified.
- zh-CN redirects unless a candidate already maps to an English FAQ and has
  existing high-confidence precedent.

## Recommended Approach

Use the existing legacy redirect pipeline. Do not add a new runtime redirect
mechanism.

`src/lib/legacy-sitemap/redirects.json` remains the source of truth. The existing
generator writes:

- `src/lib/legacy-sitemap/static-redirects.json`
- `vercel-legacy-redirects.json`
- `vercel.json`

Each new redirect rule should include the same metadata shape as existing rules:
`legacyUrl`, `legacyPath`, `target`, `type`, `confidence`, `evidence`, and
`preserveSearch`.

## Candidate Discovery

Collect candidates from three sources:

1. Current docs source links in `content/docs/en/**`.
2. Existing redirect triage reports under `docs/agents/reports/**`, especially
   API Reference docs link reports that already classify legacy Help/FAQ URLs.
3. Existing `src/lib/legacy-sitemap/redirects.json` FAQ/help rules, to identify
   nearby missing slugs and preserve established metadata style.

A candidate becomes redirectable only when:

- The legacy URL returns `404` or another non-2xx, non-3xx status when checked
  without following redirects.
- The proposed target file exists locally under
  `content/docs/en/api-reference/faq/**`.
- The proposed target URL returns `200` in production, or the local page route is
  otherwise known to be generated by this repo.
- The title, slug, anchor text, or body evidence supports a high-confidence
  Help/FAQ equivalence.

Candidates that fail these checks should be recorded in a report, not redirected.

## Content Updates

Update `content/docs/en/**` source links that still point to old Help/FAQ URLs.
Use current internal paths such as:

- `/en/api-reference/faq/integration/system_volume`
- `/en/api-reference/faq/integration/recording_mode`
- `/en/api-reference/faq/account/billing_account`
- `/en/api-reference/faq/integration/token_cohost`

For fragment links, keep the fragment only if the current FAQ page has a matching
heading slug. Otherwise, link to the page-level FAQ target.

Generated files under `public/**` and `public/llms-full.txt` are not manually
edited; they update through the normal build/output flow.

## Redirect Behavior

Redirects should be permanent `301` redirects. Query preservation follows the
existing convention:

- Preserve query params for simple path-level FAQ redirects.
- Drop query params only when an existing rule requires a query-specific target
  or when preserving a legacy platform query would produce misleading behavior.

URL fragments are not visible to HTTP servers, so fragment-specific legacy URLs
cannot be matched separately at request time. When a whole legacy path has a
single clear target with a current fragment, the generated destination may
include that fragment, following the existing `audio_format` precedent.

## Testing

Automated verification:

- Run the legacy redirect artifact check:
  `bun run legacy-redirects:check`
- Run focused legacy redirect tests:
  `bun test src/lib/legacy-sitemap`
- Run a source scan that fails if old Agora Help/FAQ links remain in
  `content/docs/en/**`.
- For substantial changes, run `bun run types:check`.

Manual verification:

- Use `curl -I --max-redirs 0` on representative old URLs and confirm `301` plus
  the expected `Location`.
- Use `curl -I` on representative target URLs and confirm `200`.

Because production may lag behind the local branch, final reporting must separate
"local redirect rule added and generated" from "production deployment now serves
the redirect".

## Risks

- Over-broad matching could redirect unrelated old Help content to an incorrect
  FAQ page. Mitigation: require high-confidence target evidence.
- Production may not immediately reflect local generated redirect artifacts.
  Mitigation: report local verification separately from production checks.
- Fragments on old URLs cannot be matched independently by HTTP redirects.
  Mitigation: only include a target fragment when the entire legacy path maps to
  a single current section.
