# 新旧站内搜索体验对比与优化建议

测试日期：2026-11-06（Asia/Shanghai）。评估方式：浏览器任务模拟与专家审阅。

本文用于评审搜索体验问题、确认优化优先级和建立回归任务集。本次 PR 整理已有测试产物，没有重新执行在线测试，也不包含搜索实现修改。两站部署版本未锁定到提交，因此这些观察只代表测试时的公开页面状态，不能作为当前版本的发布验收结论。

## 评审请求

- 优先评审新站的 S01、S02、S03、S05、S07、S08；S04、S06 是两站共有问题。
- S09–S11 为旧站对照项，用于避免继承已有体验问题；不表示要求本 PR 修改旧站。
- C01 先由内容/产品负责人确认覆盖范围，再决定是否属于检索问题。
- 确认现象、影响、优先级及验收标准后，再通过 GitHub Issues 分工和排期。文中的建议不代表已确认的实现根因。

## 范围与判定方法

- 入口：[新站搜索](https://docs-portal-staging.sh3.agoralab.co/search?q=&type=all&page=1)、[旧站搜索](https://doc.shengwang.cn/search?q=)。均为未登录状态，未参考历史搜索测试报告，未查看搜索实现源码。
- [固定查询集](2026-11-06-search-comparison-cases.csv)共 48 条：RTC 接入、功能、API、排障各 6 条，其他产品/公共内容 16 条，表达变化和边界 8 条。两站 × 两端，共 192 次基础查询。
- 桌面目标视口 1440×900；移动目标设备/可视区域 390×844，使用 Chromium 移动及触控模拟。没有覆盖真机 Safari、软键盘、输入法、系统手势和蜂窝网络。旧站部分查询的内容溢出会使布局视口变宽，见 S11。
- 基础查询从默认筛选开始，在页面输入并提交；记录前五条及首批展示结果，并选择最有希望的一个候选打开，核验实际渲染正文。目标平台是预设任务条件；未在查询里写明平台时，搜索不能据此得知用户的隐含意图。
- 成功：所选正文足以回答任务且产品/平台适配。部分成功：还需切平台、进入二级文档或补齐步骤。失败：没有候选或所选正文不能推进目标任务。正文核验不限首屏，主链接定位成本另列。
- 192 次查询中，186 次打开候选正文，6 次无可点击结果。另有 48 次交互流程、48 次筛选/改词补查、24 次浏览器内响应计时。补查不回填首轮分数，没有逐例耗尽最多五个候选和两次改词的预算。
- 两站均有分类分组。页面展示顺序和分类内位置分别记录，不能把组内第一条当作全站第一条。返回数量不代表召回率。
- 前五内验证命中只统计已打开且判定成功的前五候选，是保守下界；没有把未打开候选的标题相关性当作正文答案。

### 新站值得保留的收益

- Q14、Q15、Q17 的 API 结果前置。Q13 明确选择 Android 后，对应 joinChannel API 位于首条。

### S01：任务型“快速开始”检索未优先带到接入教程

观察：Q01 的首批结果为内容审核、云端录制及 FAQ，RTC Android 接入页未出现。Q28 只有 MCP、接入基础和开通服务，缺少完成首次对话的教程。改成“实现音视频互动”“实现对话式 AI 引擎”后，新站可找到完整教程。

用户影响：新用户通常知道自己要开始接入，却未必知道正文的正式标题，需猜测新关键词。

复现：默认全部产品/平台/类型，分别输入快速开始、对话式 AI 快速开始；检查首批结果；再输入实现音视频互动、实现对话式 AI 引擎。

建议方向：优先检查接入意图、产品限定词与导航名称的检索效果；补充“快速开始/入门/接入”等入口表达的匹配。具体索引字段与排序原因由研发确认。

建议验收：保留 Q01/Q28 作为回归任务：对应 RTC/AI 接入教程进入首批可发现位置，点击后包含实际接入步骤；不要仅提高包含“开始”二字的无关内容。

### S02：多平台合并卡片未突出默认落地平台

观察：卡片同时显示多个平台，但 Q06 默认打开 Flutter，Q07 打开 Android，Q18 打开 Electron，Q23 打开 Web。部分默认落地平台与任务设定不符。明确平台筛选后可改变落地目标。

用户影响：用户需要在打开后再确认平台，移动端平台标签占多行时尤易错读。默认“全部平台”查询并不能获知用户隐含的平台意图，此处是可辨识性与操作成本问题。

复现：输入麦克风权限，观察合并卡片；点击主标题并查看页头平台；返回，选择 Android 后再检查结果。

建议方向：在主链接旁突出当前会打开的平台；让其他平台成为可直接选择的入口。文档内发起搜索时可考虑提供沿用当前平台的可见选项。

建议验收：点击前能明确判断当前目标平台；切换平台后目标路由及正文一致；保留多平台去重的收益。

### S03：API 主标题与命中章节链接的落点不同

观察：搜索 onTokenPrivilegeWillExpire 后，主标题“频道相关”打开整页开头 getUserInfoByUid；旁边的章节链接才能到目标回调。旧站相应 API 结果直接带方法/回调锚点。章节链接本身已复测可用。

用户影响：精确方法名已经命中，主点击仍增加页内查找成本，尤其是很长的 API 页面。

复现：搜索 onTokenPrivilegeWillExpire；先点“频道相关”，记录页首；返回后点击 onTokenPrivilegeWillExpire 章节链接。

建议方向：精确 API 查询可让主点击直接定位最佳命中成员，并明确保留打开整页的入口。

建议验收：Q14/Q15/Q17 的主结果点击后，目标方法/回调位于可见区域且不被固定页头遮挡；整页入口仍可使用。

### S04：排障查询的实用 FAQ 被发版记录和 API 参数挤到后面

观察：“听不到声音”的完整无声 FAQ 位于新站展示顺序 7、旧站 13；“黑屏”为 7/11；“视频卡顿”为 10/11；ERR_INVALID_TOKEN 为 7/11。它们在 FAQ 组内通常靠前，但用户要先经过其他分组。

用户影响：结果并非没有答案，而是需要更多滚动和识别。移动端前几个屏幕常先看到发布记录、参数或术语。

复现：默认筛选输入上述四个问题词；按页面顺序寻找真正给排查步骤的 FAQ，并打开核验。

建议方向：针对问题现象、错误码等排障意图，提升有原因和解决步骤的候选可见性，或突出 FAQ 直达入口。

建议验收：排障任务的解决步骤在首批关键位置可发现，同时保留技术/API 分组与筛选；避免仅按结果总量验收。

### S05：RTM 多词任务的首批引导弱于对应 SDK 文档

观察：“实时消息 登录”首轮最有希望的候选是产品概览，仍需去快速开始；API 结果摘要偏向 RtmConfig。“实时消息 发送消息”前五条为教学场景指引，可用的 RTM 消息 API 位于展示顺序 6。旧站分别能直接找到 RTM 快速开始。

用户影响：产品名与操作组合已较明确，用户仍需识别泛场景文档、概览和 SDK 页面之间的差别。

复现：分别搜索实时消息 登录、实时消息 发送消息；对照默认结果与限定实时消息后的 login 查询。

建议方向：增强显式产品名与操作词的联合匹配；摘要优先展示 login/publish 的用途和调用信息。

建议验收：上述任务能在首批候选中识别 RTM 登录/发布消息步骤，避免用教育方案或 CLI 账号登录替代 SDK 登录。

### S06：自然语言与中文同义表达的结果仍不稳定

观察：“加入频道后听不到对方声音怎么办”在新站无结果，旧站主要给发版说明与耳机无声的特定 FAQ；缩短为“无声”后两站都能显示通用无声 FAQ。“令牌”也未直接带到 Token 生成说明。另一方面，toekn、大小写和空格用例两站都能找到 Token 内容。

用户影响：不知道正式术语的用户需要反复改词。不能由这一小组用例推断两站完全不支持语义搜索或拼写纠错。

复现：逐一输入完整问题、无声、令牌、Token；保持其他条件相同。

建议方向：评估常见问题表达和同义词；无结果时给与当前任务相关的改词建议。保留已验证有效的大小写、空格和拼写变体表现。

建议验收：Q46 至少能发现通用无声排查；Q45 能识别鉴权 Token 语境；不存在词 Q48 仍应明确无结果。

### S07：搜索摘要可见原始 Markdown 指令和内部标识

观察：Token 卡片中可见 :::info[信息]；视频降噪 FAQ 摘要含 video-enhancement-markdown-2-1-0、details 等标识；移动 acquire 卡片也露出 :::warning。已通过实际截图确认，而非仅依据 DOM 中被裁剪的文本。

用户影响：摘要空间被非正文占用，增加阅读噪声，也削弱用户对结果可用性的判断。

复现：搜索 Token、降噪、云端录制 acquire，查看相应摘要。

建议方向：在生成可见摘要时清理未渲染指令、结构标识与隐藏控制文本，同时保留有用的警告内容。

建议验收：这三类样本摘要不再显示 :::、内部段落 ID 或孤立 details；关键词上下文保持通顺。

### S08：加载更多的展开量无法通过刷新或链接保留

观察：默认 Token 查询从 11 篇加载到 19 篇，但 URL 始终 page=1；刷新恢复为 11 篇。RTC+Android 筛选下也出现 8→9→8。正常返回搜索页可保留当前展开量；刷新/重新打开链接则重置。旧站分页 URL 能保留第 2 页。

用户影响：用户难以分享或刷新后继续查看已展开的结果。查询和筛选条件本身可保留。

复现：搜索 Token，滚动到底部点击加载更多；记录条目数和 URL；刷新页面或新标签打开该 URL。

建议方向：根据产品期望保存展开批次或可恢复的结果位置；也可明确告知复制链接只代表查询条件。

建议验收：若承诺恢复已展开结果，刷新和新标签应重建相同范围及位置；至少不能丢失查询和筛选。

### S09：首页搜索框直接回车默认进入 AI 登录路径

观察：未登录状态输入 Token 后直接回车会跳到 sso.shengwang.cn；立即回车和等待建议出现后回车均复现。点击“Token - Doc Center”可正常进入无需登录的站内文档搜索。

用户影响：只想检索文档的用户被带离文档站，需要返回并重新选择入口。SSO 页的最终登录加载状态不属于本轮搜索结论。

复现：从旧站首页点击搜索入口，输入 Token，按 Enter；再返回首页，输入同词并显式点击 Doc Center。

建议方向：明确区分文档搜索与 AI 提问的默认动作；文档检索入口的回车应符合用户预期。

建议验收：未登录用户可从首页用键盘完成文档搜索；AI 提问仍可通过明确选项进入。

### S10：同一文档多个章节重复占据前五条

观察：主体样本中，旧站有 12/40 条查询的前五结果包含相同页面的重复章节链接；新站为 0/40。“屏幕共享”旧站前三条即同一 Android 页面及章节；新站将多平台和命中章节合并。这里只统计相同 URL 去掉 hash 后的重复，不把不同产品文档误算为同页。

用户影响：前五条看起来多，但独立可选文档较少；用户要越过重复章节才看到其他平台或内容。

复现：搜索屏幕共享或跨频道媒体流转发，比较前五 URL 去掉 hash 后的分布。

建议方向：保留命中章节定位的优势，同时按文档聚合，展示可展开的章节入口。

建议验收：相同文档不再连续占用多条主结果；展开后各章节仍可直接定位。

### S11：部分 REST 长路径将页面布局横向撑开

观察：物理/可视区域为 390×844、触控开启时，“云端录制 acquire”的页面布局和内容宽度为 812 px，新站同词为 390 px。旧站出现页面级横向滚动，API 长路径不能在当前可视宽度内完整展示。可视 viewport scale=1，不能将其描述为浏览器主动缩小。

用户影响：移动端需要横向移动才能读完部分结果，产品/平台及长接口名的识别成本上升。

复现：使用 390×844 移动模拟，搜索云端录制 acquire，向下滚动到 API 卡片；观察横向滚动条和长路径。

建议方向：约束结果卡片及长标识符的最小宽度，允许路径换行或局部滚动；保持页面本身适配设备宽度。

建议验收：同查询下页面宽度不被长路径撑大，API 名称和产品标签可读；桌面展示保持正常。

### C01：灵动课堂对应内容范围尚未确认
