# Migration Verification Checklist

This file defines what acceptable migration evidence looks like. It answers: "What must be checked before a row can be marked `done`?"

Do not use this file as a progress tracker. Record actual verification evidence in the `verification` field of `migration-ledger.csv`, and reference any accepted exception through `decision_refs`.

Use this checklist before marking any migration ledger row `done`.

## Universal Checks

- [ ] Source path is recorded.
- [ ] Target path is recorded and matches `path-map.csv` or an approved exception.
- [ ] Migration action is recorded.
- [ ] Risk level is recorded.
- [ ] Batchability is recorded as `yes`, `partial`, or `no`.
- [ ] Blocker field is empty or explains the remaining blocker.
- [ ] Next step is concrete.
- [ ] Status is one of the approved `spec.md` statuses.
- [ ] Final content follows `docs/agents/markdown-authoring-standard.md`.
- [ ] Reusable legacy component and syntax conversions match `docs/migration/component-map.yaml`.
- [ ] Batch/scripted migration records matched component-map rules and review flags in the component usage report when applicable.
- [ ] Verification field names the command or manual review performed.

## Prose And MDX Pages

- [ ] Legacy Docusaurus JSX has been removed or converted.
- [ ] Callouts use approved directive fences.
- [ ] Code blocks have languages and valid tab metadata when needed.
- [ ] Tabs, if used, follow the approved Fumadocs-compatible structure.
- [ ] Platform variants are static files/folders or approved platform blocks.
- [ ] Shared imports are converted to includes or static expansion.
- [ ] Nested shared dependencies are resolved or explicitly blocked.
- [ ] Legacy frontmatter fields are removed.
- [ ] Lists, callouts, code fences, tables, and images have valid blank lines and indentation.
- [ ] Source meaning, headings, examples, warnings, and important constraints are preserved unless the action is `rewrite`.

## Links, Anchors, And Assets

- [ ] Internal links point to migrated target routes or are recorded as unresolved follow-up work.
- [ ] External links are preserved unless an approved decision replaces them.
- [ ] Legacy stable fragment IDs are preserved when old links depend on them.
- [ ] Images use Markdown syntax where possible and have useful alt text.
- [ ] Missing images, sizing issues, captions, or path questions are recorded.
- [ ] Static assets are in the approved `public/**` location or remain valid remote assets.

## Shared Content

- [ ] Shared dependency chain is known.
- [ ] Multi-product shared content is pruned only by explicit product/platform scope, not by summarizing.
- [ ] Runtime variables such as `props.*` or `frontMatter.*` are expanded, split, or blocked.
- [ ] Reusable target shared files follow the same authoring standard as normal pages.
- [ ] Include paths are relative and stable from the target page.

## Platform And Versioned Content

- [ ] Platform keys match the repository platform registry.
- [ ] Platform pages or folders preserve the intended navigation shape.
- [ ] `meta.json` page order matches the approved IA.
- [ ] Independent product or platform navigation uses `navScope` when required.
- [ ] Version folders are placed under the correct platform/product folder.
- [ ] Current-version clean URLs use the approved `(current)` pattern when required.

## HTML API Reference Conversion

- [ ] Legacy `html-docs/**` source path is recorded.
- [ ] Legacy TOC tree is captured before conversion.
- [ ] Target folder tree preserves the old nested navigation unless an approved decision changes it.
- [ ] Each folder that needs navigation has `meta.json`.
- [ ] Category pages that own descendants become folder index pages when appropriate.
- [ ] Stable fragment IDs are preserved.
- [ ] Inline links, `xref` references, and code spans remain clickable/readable.
- [ ] Notes, definition lists, parameter sections, return values, and nested lists are structurally preserved.
- [ ] Literal `<`, `>`, `{`, and `}` outside code are escaped or wrapped safely.
- [ ] Generated pages compile as MDX.

## OpenAPI Lane

- [ ] OpenAPI YAML/JSON source lives under `content/openapi/**`.
- [ ] No OpenAPI YAML/JSON is placed under `content/docs/**`.
- [ ] Public `/openapi/**` output is generated by sync/build, not hand-maintained as source.
- [ ] Endpoint route mapping is represented through the approved OpenAPI lane registry when renderer work is involved.
- [ ] `operationId` mapping is complete and unique when endpoint pages are generated.
- [ ] Search, llms, locale links, prerender paths, and sidebar behavior are covered when route behavior changes.

## Recommended Commands

Run the smallest command set that matches the touched surface:

```bash
bun run docs:mdx-build-syntax
bun run types:check
```

Use `docs:mdx-build-syntax` as a fast preflight before a full build. It catches
common migrated MDX syntax and structure patterns that block Fumadocs/Vite
builds, but it does not replace `bun run build`.

Add these when relevant:

```bash
bun run test
bun run lint
bun run openapi:sync
bun run build
```

Command success is necessary for many changes, but it is not enough by itself. Record manual content checks for migrated prose, shared expansion, platform grouping, HTML API conversion, and OpenAPI rendering.
