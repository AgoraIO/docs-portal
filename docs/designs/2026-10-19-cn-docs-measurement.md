# 新中文文档成效与搜索分析方案 v1

日期：2026-10-19。状态：P0 已实施并完成 staging 功能、收数、隐私和桌面/手机界面验收。业务采集、反馈界面、共享计算与三个看板已接好；生产尚未启用。实际看板见 [配置回执](../analytics/posthog-artifacts.json)。SDK 操作步骤的正确性仍待产品负责人核验。

适用范围：`deployment_region=cn`、`locale=zh-CN` 的新中文文档。采集平台沿用 [PostHog 项目 509917](https://us.posthog.com/project/509917/home)。

## 先看这一页

**目标：知道用户的问题是否解决、答案是否正确、过程是否够快、信息是否容易使用，并据此决定先改什么。**

采用 KCS 的自助服务测量方法、Google HEART 的“目标 → 信号 → 指标”方法。搜索事件参考 Algolia、Mintlify；数据规范参考 Tracking Plan。方法与产品比较见 [研究依据](./2026-10-19-docs-measurement-research.md)。以下是适配本项目的方案，不是照搬某家厂商的全部指标。

| 建设部分 | 第一批交付 | 直接回答 |
| --- | --- | --- |
| 用户使用过程 | 把入口、搜索、可见结果、阅读和反馈关联起来；也覆盖直接打开文档的访问 | 用户找什么、卡在哪里、最后反馈什么 |
| 成效与体验 | 解决情况、确认解决耗时、易用性；始终显示样本和未知状态 | 有没有解决、快不快、好不好用 |
| 内容正确性 | 首批 20 个真实问题场景，核验结果适配和操作步骤 | 答案对不对、哪些错误必须先修 |
| 统一数据与看板 | 一份事件与字段规范、一套计算规则、三个用途明确的小看板 | 同一批数据能持续回答新问题 |

实施分三期：**P0 收准并形成基线 → P1 定位原因并推动修复 → P2 关联真实业务结果并验证重大改动。** 每期按验收结果推进，不先承诺没有依据的提升幅度或交付日期。

## 1. 要回答的问题

这些是问题目录，不是十个并列主指标。“首批”只代表能观察到相应数据，不代表能完整回答所有因果问题。

| 问题类别 | 代表问题 | 主要证据 | 首批范围 |
| --- | --- | --- | --- |
| 用户与入口 | 用户从哪里来？在看哪个产品、平台、版本？ | 入口、当前页面与选择的上下文；身份未知单列 | P0；浏览上下文不等于用户实际 SDK 环境 |
| 用户需求 | 想做什么？哪些需求没有文档覆盖？ | 脱敏查询、明确任务反馈、支持样本 | P0 查词与个案，P1 归类；猜测意图标为推断 |
| 查找与导航 | 搜不到、排得低、筛错，还是目标打不开？ | 可见结果、排名、筛选、选择、实际到达、错误 | P0 两种全站搜索入口；P1 FAQ 本地筛选 |
| 内容质量 | 产品、平台、版本对吗？内容过期或步骤有错吗？ | 内容上下文、原因反馈、固定问题核验 | P0 代表样本，P1 扩大样本 |
| 解决结果 | 解决、部分解决、未解决，还是尚未验证？ | 与本次过程关联的用户反馈 | P0；无反馈保留未知 |
| 速度与可靠性 | 结果多久出现？确认解决花多久？哪些请求失败？ | 可见结果耗时、过程时间、失败状态 | P0 浏览器侧；P1 服务端诊断 |
| 易用性 | 是否容易找到、看懂并使用信息？ | 易用性单题、页面反馈、结构化原因 | P0；不靠停留时间推断 |
| 修复优先级 | 哪些问题先修？应补内容还是调搜索？ | 需求量、明确未解决、错误严重度、核验结果 | P0 人工分流，P1 形成修复清单 |
| 改动效果 | 改文档、排序、导航后，同类任务是否改善？ | 发布版本、固定评测集、可比人群或实验 | P1 前后描述；P2 受控实验 |
| 后续价值与证据质量 | 是否仍求助或完成集成？有多少过程无法判断？ | 工单、产品成功事实、可靠关联、观测覆盖 | P0 覆盖与未知；P2 业务结果 |

## 3. 统计单位与关联

**以一次“求助过程”为观察单位。** 它是可记录的连续使用上下文，不声称自动识别用户真实问题的边界。一个用户可以有多个过程，一个过程可以有多次搜索和多篇阅读。PostHog 的访客、会话与求助过程分别保留。

| 标识 | 创建与使用规则 |
| --- | --- |
| `journey_id` | 首次有效搜索或首次文档正文可见时创建；后续改词、筛选和阅读沿用。同一标签页刷新保留；显式开始新问题或连续 30 分钟无活动后新建。30 分钟是 v1 观察参数，不是问题解决标准 |
| `search_id` | 每次有效提交的查询词或筛选条件变化创建。翻页、重试、预取和版本 facets 不另算一次逻辑搜索 |
| `request_id` | 每次真实网络尝试创建，区分 `results/facets/prefetch`、页码和重试次数。通过校验后的请求头关联，不随意增加现有 API query 参数 |
| `results_view_id` | 一份真正展示的结果快照，复用展示事件的 `event_id`。每行结果持有其原始上下文；点击旧结果不能归到输入框里的新查询 |
| `doc_view_id` | 一次规范文档与所选平台、版本的可见主体视图。重渲染、去尾斜杠、清理归因参数不重算；真实切换内容上下文则建立新视图 |
| `event_id` | 一次事实的唯一身份；发送重试复用。计算层去重，不能只靠组件挂载次数 |

各标签页独立管理当前过程。通过搜索结果打开新标签页时，用短期、同源、无查询正文的标识传递原过程；普通新标签页不自动继承另一个标签页的最近搜索。中键、Cmd/Ctrl 点击、存储不可用和账号切换都要验收。无法关联就记 `unknown`，不强行拼接。登录不自动更换过程，账号切换清除当前关联，避免串账号。

v1 按过程开始日形成统计批次，接收开始后 24 小时内的结果反馈，取同一问题最后有效回答。未满窗口的批次标为未成熟；窗口后的反馈保留并单列，不悄悄移动分母。跨过程回评必须明确指向原过程。30 分钟分段、24 小时观察窗分别版本化，后续按任务样本校准。

## 4. 成效指标与质量约束

先运行三个主指标。所有比例同时展示分子、分母和未知状态。时间按同一入口和同类任务比较，失败与未完成另列；暂无分母时显示“暂无有效样本”。

| 类型 | 指标与计算规则 | 解读限制 |
| --- | --- | --- |
| 主指标 1 | **反馈过程中的完整解决率**：最后有效回答为“解决”的过程 / 回答为“解决、部分解决、未解决”的过程 | 尚未验证、无回应分别列出；不能外推为全部用户的真实解决率 |
| 主指标 2 | **到确认解决的耗时 P50/P90**：从过程首次有效搜索或正文可见，到最终有效解决状态对应的明确反馈 | 包含反馈延迟；只描述已确认解决的样本，必须同看解决情况与未知占比。重复同值不重置时间；改为其他状态则撤销原完成锚点，再次明确解决时使用新的反馈时间 |
| 主指标 3 | **反馈过程中的易用率**：最后易用性回答为 4–5 分的过程 / 有有效 1–5 分回答的过程 | 同时展示完整分布、回答数与反馈来源。量表是本项目定义，不直接套用行业 CES/NPS 基准 |
| 质量约束 | **已审核场景正确适配通过率**：搜索结果适配与目标步骤核验均通过的场景 / 已审核场景 | 仅代表核验样本。阻断级错误独列，不能被平均值掩盖；未审核不算通过 |
| 必备披露 | **结果可知度、反馈响应率、采集覆盖**：有解决结论 / 已观察过程；有效回答 / 实际看到对应问题的过程；已接入入口与未知关联情况 | 两个比例分母不同；反馈样本只代表回答者，采集被拦截的访问无法自动计入总量 |

诊断指标首批限制为：无结果、搜索失败、可见结果耗时、反复改词、目标到达和问题原因。零结果只算成功且实际展示为空的搜索；错误不是零结果。搜索弹窗的章节行、搜索页的文档卡片分别命名排名和计数，不把两种单位混成一个平均排名。

弹窗计时从最后一次有效输入（含输入法组合结束）到正确当前结果实际可见，包含防抖、网络和渲染；完整搜索页从提交或筛选动作起算。分页耗时单列。跨页过程使用可校验的时间戳；负时长、时钟异常和缺失记为无效时间样本，不能补零。

上线后先观察 14 个完整自然日作为初始基线；样本不足继续积累。该时长不是统计显著性的保证。目标值由基线、质量样本和实际改进成本决定，本方案不编造当前解决率或提升承诺。

## 5. 用户反馈怎么问

保留现有“本页是否有帮助”。新增针对本次过程的两个独立问题，不把页面点赞解释为任务完成。

| 问题 | 回答 | 用途 |
| --- | --- | --- |
| 这次找到的信息解决你的问题了吗？ | 解决 / 部分解决 / 未解决 / 尚未验证 | 记录用户自报结果；不回应保持未知 |
| 找到并使用这些信息有多容易？ | 1 非常困难至 5 非常容易 | 记录努力程度；可以独立回答或跳过 |
| 哪一步没有帮上忙？ | 找不到、不相关、产品/平台/版本不对、过期、内容错误、看不懂、步骤无效、太慢、其他 | 结构化原因可多选；不强迫填写正文 |

反馈入口也覆盖无结果和错误状态，不只询问已经点击或读到页底的人。持续入口允许主动反馈；主动邀请采用在过程开始时确定的稳定抽样。v1 建议邀请 10% 的合格过程，同一可识别访客 24 小时最多一次，不自动弹出阻断式对话框。抽样率、频控、邀请位置和文案版本均记录，属于待校准配置，不是行业标准。

反馈入口提供“开始新问题”的轻量操作，供用户主动分开上下文；不要求每次搜索前先填写任务。

分别记录：具备邀请资格、被抽中、受频控限制、真正可见、回答与修正。组件 mount 不等于用户看见问题。来自抽样邀请和用户主动打开的反馈分开分析；过程跨页只保留一份邀请身份。存储不可用时保守控制提示并标记频控状态。

页面帮助度、过程解决情况、易用性是不同问题。一次回答只进入一个正式数据协议。首批保留 `docs_page_feedback` 的事件名并补齐上下文；新增问卷用自有界面与现有采集入口统一发送。PostHog Surveys 可作为后续管理界面，若采用，必须做明确映射，不能让相同回答同时重复计入两套事件。

## 6. 统一采集规范

统一模块负责事件名、类型、字段白名单、脱敏、身份、去重与版本。各界面只提交真实发生的业务事实。事件名和字段使用 `lower_snake_case`，耗时为毫秒并以 `_ms` 结尾，排名从 1 开始，缺失用 `null/unknown`。

### P0 事件

| 事件 | 触发事实 | 关键上下文 |
| --- | --- | --- |
| `docs_journey_started` | 首次有效搜索或正文可见，幂等创建过程 | 入口、观察规则版本、邀请抽样与资格 |
| `docs_search_submitted` | 防抖/输入法处理后的有效查询，或明确提交的筛选变化 | 搜索身份、父搜索、入口与条件；非逐按键 |
| `docs_search_results_presented` | 当前有效结果已进入可见界面；包含空结果 | 结果快照、来源请求、计数单位、页码、可见耗时 |
| `docs_search_failed` | 有效搜索实际呈现错误状态 | 网络/HTTP/解析/渲染、受控错误码；过期请求中止不算用户失败 |
| `docs_search_result_selected` | 实际通过鼠标、键盘、中键等选择结果 | 原结果快照、结果身份、所见排名、目标文档 |
| `docs_content_viewed` | 正确内容主体实际可见；不是发起导航、骨架或 404 | 规范文档、平台、版本、视图与可靠的搜索归因 |
| `docs_feedback_prompted` | 对应反馈问题进入可见区域 | 邀请/问题身份、范围、来源、抽样与文案版本 |
| `docs_feedback_submitted` | 新问题的有效回答或修改 | 过程/视图、问题身份、受控答案、修订号、反馈来源 |
| 沿用 `docs_page_feedback` | 现有本页帮助度表态 | 补曝光与通用上下文；只计页面帮助度，不重复发为过程解决 |

`docs_journey_started` 可由首条业务事实补建，避免异步发送顺序导致孤立过程。发生时先保存时间与上下文快照，SDK 加载或发送延迟不能改读后来的 URL 和输入框。任何缺少起点、原始快照或有效关联的事实都标记缺口，不按“最后一次搜索”猜测来源。事件输出与重试不能阻塞搜索、跳转或反馈交互。

P1 增加服务端 `docs_search_request_completed`、公共动作 `docs_content_action`、搜索入口 `docs_search_opened`，以及带独立 surface 的 FAQ 查询事件。点击下载只能记意图，Clipboard API 成功才能记复制完成，打开 GitHub 反馈页面不能记为工单提交。

### 共同字段

| 字段组 | 要求 |
| --- | --- |
| 事件时间与来源 | `occurred_at` 保存事实发生的 UTC 时间，`event_source` 区分浏览器、服务端与质量运行器；接收时间来自实际采集系统，不由浏览器伪造 |
| 范围和版本 | `schema_version`、`site_id=docs_portal`、`deployment_region=cn`、`locale=zh-CN`、`environment`、`app_release`、`traffic_type`；测试明确标记 |
| 关联 | 过程、搜索、请求、结果快照、内容视图与事件身份；`attribution_status`；访客与账号沿用已有可靠身份协议 |
| 内容 | 规范路径、文档身份、`content_type`、产品、所选平台/版本、内容发布版本；解析规则版本化，不把未选平台猜成 Web |
| 搜索 | 入口、经过脱敏且限长的查询、有效筛选、结果类型与排名、实际索引和策略版本；未知索引版本留空，不能拿前端 SHA 冒充 |
| 反馈和证据 | 问题/邀请身份、范围、受控回答、修订、抽样/主动反馈、观察规则；证据区分行为、自报、推断和核验 |

首版文档身份可由内容来源标识与规范路径解析，不假定迁移前后 URL 天然同一文档。入口保留域名与安全的页面类别，不保存任意 referrer 查询参数。发布时生成实际内容、应用、索引的版本关系；数据里缺少哪一项就明确缺少。

## 7. 数据怎样复用

以原始事实为基础，维护以下四类逻辑数据集和一份核验结果。第一期先用 PostHog SQL insight/保存查询实现，不额外搭建数仓；是否建立物化视图由实际性能和权限决定。

| 数据集 | 一行代表什么 | 负责回答 |
| --- | --- | --- |
| `docs_journey_facts` | 一个可观察求助过程 | 入口、步骤、最终反馈、确认耗时、未知与覆盖 |
| `docs_search_facts` | 一次逻辑搜索 | 条件、结果、失败、选择、到达与耗时 |
| `docs_content_view_facts` | 一次真实内容视图 | 页面与上下文、来源、帮助度、后续行为 |
| `docs_feedback_facts` | 一个范围与问题的最后有效回答 | 解决、易用性和原因，保留修订原始记录 |
| `docs_quality_results` | 一个问题场景在一次发布中的核验 | 搜索相关性、上下文适配、步骤验证、严重度与审核人 |

按 `event_id` 去重，并按实体与问题身份处理反馈修订。过程反馈以 `(journey_id, question_id)` 取最后有效回答；页面反馈另含 `doc_view_id` 和页面范围，不能把一次过程反馈分摊成多篇文档各解决一次。以全部已观察过程为起表，关联反馈和后续事实，不能只从有反馈记录建表而丢掉未知。每个共享指标记录名称、版本、负责人、单位、分子分母、时间窗、排除规则与生效发布。

访客/会话漏斗可用于探索路径。正式解决率按 `journey_id` 计算，不直接拿“人数漏斗”代替。不同过程、不同版本或阶段不能因同一用户而混合；总转化与相邻步骤转化分别解释。临时追问复用共享计算规则，不能为了每张图另写一套分母。

## 8. 第一批三个看板

| 看板 | 主要内容 | 看完要做的决定 |
| --- | --- | --- |
| **成效与证据** | 三个主指标、结果分布、质量核验、样本、反馈响应与未知 | 哪些任务或人群需要优先改善；证据是否够用 |
| **搜索与查找** | 查询需求、无结果、失败、所见排名、改词、内容到达、可见耗时 | 补内容、修元数据、调召回排序，还是修性能与跳转 |
| **内容改进** | 文档/产品/平台/版本的问题原因、未解决样本、严重错误、修复状态与复验版本 | 哪些内容先修、由谁处理、修改是否通过复验 |

共同过滤：正式生产流量、中文发布范围、时间、入口、产品、平台、版本、发布号；结果分组同时显示有效样本量。无法观测的字段显式未知。测试、staging、local 独立；生产灰度和全量的覆盖范围分别注明。用户任务类别必须来自明确反馈、审核归类或标记的推断。

没有基线时展示“尚未测得”，不塞演示数值。默认展示完整自然日，未成熟结果单列；时间保存 UTC，业务报表明确按 Asia/Shanghai 展示，不在本方案中自动修改 PostHog 项目时区。

## 9. 正确性与内容修复

P0 从现有中文质量查询集选择并补足 **20 个真实任务场景**。20 是首批工作量建议，不是统计代表性保证。覆盖精确 API 名、中文同义词、产品/平台/版本、鉴权与排错，并包含应该无结果、错误输入和已知风险案例；不声称这些是现网最热门问题。

每个场景记录：用户任务、允许上下文、查询和筛选、预期文档/章节、核验步骤、严重度、负责人、内容/索引/策略版本。分开检查：前三个实际展示单位中是否出现适配结果；目标文档是否真的可完成任务。纯导航任务检查到达与信息适配，不强行要求执行代码。

失败分类使用 `ranking_miss/wrong_context/content_wrong/content_stale/broken_target`。阻断级错误指可能造成错误集成、凭据泄露、数据损失，或关键路径完全不可用的已知缺陷。P0 验收集内不得留有未处理的阻断级缺陷，普通缺陷单列，不用平均分抵消。

保留固定回归集，新增真实样本形成独立评估集，避免反复针对同一批题调参后宣称普遍改善。AI 可在脱敏后辅助归类，不能单独充当正确性裁判。人工反馈形成待办，再核验、修复、记录发布并复验。

## 11. 采集边界

- 最终发送层覆盖业务事件、URL、referrer 和 SDK 合并的持久属性，先脱敏、限长再发送。疑似密钥、Token、手机号、邮箱和客户私有链接不保留原文；hash 不等于脱敏。
- 首批不采集自由反馈正文、完整代码块、SSO 查询或认证 cookie；也不因本方案打开录屏。敏感失败原因可用结构化枚举处理。
- 浏览器拦截、离线、退出和存储不可用的损失要披露。无可靠队列时不承诺全部到达。发送失败不影响用户操作。
- 观测范围只含已发布、已接入且合格的过程。未曝光、未回答、尚未验证和无法关联分别保留，不能统称未解决。

## 12. 分期、产物与验收

| 阶段 | 必须完成的产物 | 通过条件 |
| --- | --- | --- |
| **P0：收准并形成基线** | 事件/字段规范与版本；统一数据出口；两种搜索入口、全类型正文到达与反馈；共享计算规则；三个看板；20 场景核验；staging 到生产的回执 | 受控过程数量与事件一致，敏感字段检查通过，未知不算失败，验收集无未处理阻断级缺陷；生产全量开始时间与覆盖明确 |
| **P1：定位并推动修复** | FAQ/公共动作、服务端诊断、需求与原因归类、问题分派、扩大质量集、修复复验与版本对比 | 能将问题分到内容/元数据/召回/排序/性能/跳转，能追踪负责人和复验结果 |
| **P2：关联真实结果** | 同一任务的工单或产品结果关联、重大改动的实验、业务价值计算 | 已验证来源、可靠关联、窗口与覆盖；普通相关不宣称因果，避免用下载点击代替成功集成 |

P0 的端到端验收至少包括：

1. 中文输入法和 200ms 防抖只有一次有效提交；被替代的请求不计失败或展示。
2. 选版本所需 facets、翻页、重试不扩大逻辑搜索分母；累计结果去重、排名单位正确。
3. 等待新结果时点击旧结果，仍关联旧快照；鼠标、键盘、中键和新标签页正确。
4. 空结果、网络错误、超时和渲染失败分开；错误状态也有反馈机会。
5. 静态直达、SPA、MDX、平台内容和 OpenAPI 真正正文到达；骨架/404不计，规范化不重计。
6. 单页与过程反馈分开；邀请跨页不重复，修改只计最后有效状态；无回应与尚未验证保持未知。
7. 同一用户两次过程、并行标签页、账号切换与无存储不串联。
8. 搜索词及默认 URL/referrer 中的敏感内容在实际出站负载中被排除；不只测试 capture() 入参。
9. SDK 初始化一次；禁用或发送失败不阻塞正文、搜索、跳转与复制。
10. 在项目 509917 按受控 `test_run_id` 核对接收事件和去重后的过程/搜索/反馈数，再验三个看板；测试不进入正式指标。

受控验收要求该场景的已发、已收到与聚合结果可核对，不能将它外推为生产浏览器 100% 送达。代码实现完成后运行相关组件/归因测试、`bun run test`、`bun run types:check` 与 lint，构建并复验静态输出和现有搜索/登录/跳转。

## 13. 发布、回退与日常使用

本节保留发布路径。staging #107 完成全面功能验收；最终版本 `e113a4246` 随 #108 正常完整构建发布成功，9 类事件、共享事实、隐私、20 场景检索及所有发布检查再次通过。选中态对比度已修复，桌面深浅主题及手机实际截图已放入 PR #1212。生产参数已备好，业务采集与新反馈开关仍关闭。生产启用时间与覆盖须在实际发布后记录。

1. 从中文源分支实现与测试，更新部署构建参数；在 staging 正常应用构建，核对源版本、内容与索引关系。
2. 使用明确标记的受控访问完成上节验收，保存事件清单、查询规则版本和发布回执。页面成功不能代替 PostHog 收数验证。
3. 生产先小范围验收再全量；范围和生效时间分别记录。全量前的数据只描述该范围，不与全量基线混比。
4. 生产完整基线形成后，评审首批结果与样本。重大问题立即分派，普通问题每周归类；这是一项建议工作节奏，本方案不创建自动通知。
5. 回退业务采集与新反馈时使用已验证关闭开关的应用镜像。开关是构建配置，回退需要发布工件；不承诺无需发版即可关闭。保持内容、后端与索引的兼容关系，先验证再恢复。

| 责任角色 | 负责的结果 |
| --- | --- |
| 文档产品负责人 | 问题目录、反馈文案、目标与修复优先级 |
| 前端/搜索工程师 | 事实触发、归因、隐私出口、查询与搜索性能 |
| 各产品内容负责人 | 真实任务、平台版本适配、步骤核验和内容修复 |
| 数据口径负责人 | 共享计算规则、样本与未知披露、看板一致性 |
| 发布负责人 | 构建参数、staging/prod 回执、回退验证 |

具体人名和首批任务审核人需在实施启动时落实。P2 外部系统与可靠任务标识尚未确认，因此第一期不能宣称回答了“成功集成了多少”或“减少了多少成本”。

## 14. 方案默认项与实施拆分

本稿建议的默认项：三个主指标；20 个首批场景；过程 30 分钟无活动分段；24 小时反馈观察窗；10% 主动邀请、访客 24 小时一次；全量后先观察 14 个完整自然日。它们不是现网测量值或行业基准；上线前形成带版本的配置，发现覆盖或任务不适合时校准。

实施按依赖拆为：**A 契约/数据出口 → B 搜索与正文事实 + C 反馈 → D 共享模型/看板与质量核验 → E staging 验收与生产发布**。B、C 都依赖 A，D 依赖对应事实和样本，E 依赖前项验收。质量任务清单可在 A 阶段准备。此处是工作包，不是在未经确认的外部项目中创建任务。
