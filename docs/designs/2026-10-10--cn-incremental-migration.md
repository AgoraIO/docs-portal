# 中文文档增量迁移设计

## 目标

将 `shengwang-doc-source` 的 `master` 从已记录 checkpoint 之后新增或变更的中文文档内容，审计并迁移到 `docs-portal` 的 `CN-NEWDOC`，保留语义、版本、平台差异、资源、链接和导航关系，并为每个源文件留下可复核的迁移状态。

## 基线与范围

- 源已审查基线：`474985f901fffffd4ffed27ed35a060f986bdb98`。
- 上次迁移截止：`2026-08-03T08:55:38Z`，对应源 PR #2061 合并提交 `f180f4676c5d514a8abee21748fdf637ba67d4f7`。
- 当前源：远端 `master`，审计时记录实际 SHA。
- 当前目标：远端 `CN-NEWDOC`，以最新远端 SHA 为基础。
- 源工作区未提交改动不纳入范围。

## 流程

1. 按源首父历史和 GitHub 合并时间列出 checkpoint 之后的候选提交与 PR。
2. 对每个候选文件分类：可迁移正文、平台变体、资源/导航、OpenAPI、生成产物、站点实现或明确跳过项。
3. 以目标内容和历史 PR 为证据确认是否已经存在，避免重复迁移。
4. 将可迁移内容转换为 Fumadocs 支持的 Markdown/MDX；生成 HTML/API 产物遵循现有 API 迁移规则，不能机械复制站点实现。
5. 持续维护审计清单，记录源路径、变更类型、目标路径、状态、人工确认、验证和跳过原因。
6. 运行针对性语法、链接、导航、资源、类型、测试、构建和 `git diff --check` 验证。

## 非目标与边界

- 不迁移旧站站点实现代码、生成版本元数据或无法映射的生成产物。
- 不覆盖目标已有内容，除非源变更与目标文件映射明确且审计记录说明原因。
- 不修改与本批次无关的目标文件。

## 风险与人工确认

- 源文件可能已在目标分支通过其他 PR 进入；以内容核对和目标历史为准。
- API HTML、OpenAPI、复杂 JSX/HTML 和导航变更需要单独标记，不能仅凭路径判断。
- 无法一一映射的文件保留在审计清单中，并记录决定与后续动作。

## 验证策略

- 源差异闭合检查。
- Markdown/MDX、内部链接、图片、平台块和导航检查。
- `bun run types:check`、相关测试、必要时 `bun run lint`、`bun run build`。
- `git diff --check`。
