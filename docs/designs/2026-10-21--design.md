# RESTful API 导航 HTTP 方法配色修复设计

状态：用户已确认推荐方案；实现采用共享方法配色函数。

## 目标与已确认事实

从 `origin/codex/cn-newdoc-html-api-migration`（检查时为 `ae9df4c39`）创建修复分支 `codex/fix-restful-sidebar-method-colors`，覆盖所有使用共用导航的 RESTful API 产品。

目标分支中，`DocsSidebarTree.tsx` 的 `SidebarPageLabel` 已输出 HTTP 方法文字，但固定使用 `text-[color:var(--ink-4)]` 灰色。`DocsShell.tsx` 的移动导航也独立输出相同的灰色标签。正文 `FumadocsOpenApiContent.tsx` 的 `OPENAPI_METHOD_BADGE_CLASSES` 则按方法区分颜色。因此代码证据表明是样式未对齐，浏览器复现与计算样式验证将在实现阶段完成。

导航与正文对同一方法使用一致配色，用户可快速扫描定位；修复同时覆盖桌面和移动导航，沿用已有端点数据及路由。

## 可选方案

1. **推荐：抽取共享方法配色函数。** 将正文已有映射移到可供客户端导入的轻量模块，正文、桌面导航和移动导航共同使用；保留各处标签尺寸及结构。改动集中，避免配色漂移，也不需要让导航导入体积较大的正文组件。
2. **抽取完整方法徽标组件。** 统一结构、配色和尺寸变体，长期复用更强，但需要兼容正文现有 `Badge` 的结构、选择器与行为，本次改动面更大。
3. **仅给导航补充 CSS 颜色。** 改动少，但复制方法映射，后续仍可能与正文不一致，不推荐。

## 推荐方案的行为与边界

- 复用现有语义颜色：GET 蓝、POST 绿、PUT/PATCH 琥珀、DELETE 红，同时沿用对应的深色主题颜色。
- 当前 OpenAPI YAML 使用 GET、POST、PUT、PATCH、DELETE 五种方法，均有正文配色。共享入口规范化方法大小写并集中处理其他方法的中性回退。
- 方法标签文字继续可读，不单独依靠颜色传达请求方法。
- 导航默认、悬停、选中及键盘聚焦时，标签配色保持清晰；避免父级导航颜色覆盖方法颜色。
- 不改变端点标题、排序、目录层级、URL、OpenAPI 数据及正文交互；无方法字段的普通页面继续不显示徽标。
- 不引入服务端模块依赖，不改变静态部署架构，不修改生成文件。

## 后续修复：API 参考平台筛选

API 参考目录保留平台/语言选择，Android、iOS、Web 等常用项优先，产品顺序保持原有能力分组。产品选择在桌面和手机均显示，有筛选时始终提供清除入口。

筛选按产品、API 类型、平台的顺序统一规范化。产品决定可用 API 类型，不支持的类型禁用；产品和类型共同决定平台/语言选项。切换时保留兼容选择，清理不兼容选择，避免 RTMP 网关与 iOS 等无效组合进入空结果。

RESTful 只作为 API 类型，选择后平台控件停用并显示不适用；平台下拉不重复提供 RESTful。旧链接中的 platform=restful-api 迁移到 apiType=restful，移除冗余参数。URL 初始化、历史恢复和控件切换使用同一校验逻辑，并保留其他查询参数和锚点。

Windows 筛选覆盖明确适用于 Windows 的 RTC C++ 全平台、RTC C# Windows 和 IM C++ Windows 文档，并在当前产品的平台选项中补入派生的 Windows 选项。兼容规则按已核实的文档族集中维护，避免将其他操作系统的 C++ SDK 推断为 Windows SDK；原始链接和 SDK 语言入口均保留。

回归检查覆盖此前评审发现的四个问题、兼容选择保留、URL 分享及历史恢复。完整中文站预览继续使用全部内容，不限定 RESTful 区域。
