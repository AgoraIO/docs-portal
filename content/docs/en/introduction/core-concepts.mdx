An Agora integration uses a project to identify the application and the credentials required by its services. Your client presents the experience to users; your backend handles the secret credentials and service operations the integration needs.

Use these concepts when a quickstart asks you to create a project, supply an App ID, or configure authentication.

## Account, project, and Console

Your **account** gives you access to Agora Console. A **project** holds an App ID, service configuration, and credentials for an application or environment. You can manage multiple projects from the same account.

**Agora Console** is the management interface for accounts, projects, service settings, usage, and billing. It is where you create a project and retrieve its configuration.

For the setup steps, follow [Account](/en/introduction/account). For detailed Console operations, see [Console Setup](/en/introduction/console-setup).

## Project credentials and authentication

| Value | What it means | How it is used |
| --- | --- | --- |
| **App ID** | The identifier assigned to an Agora project | Used by clients and service requests to identify the project. It does not replace the authentication required by a service. |
| **App Certificate** | A project credential used to generate authentication tokens | Used on your backend. Keep it out of client applications and public repositories. |
| **Token** | An authentication value with permissions and an expiry | Supplied to the SDK or API that requires it. Its fields and scope depend on the product and operation. |

For an RTC application, a client joins a channel using the identity and token required by its configuration. For a production integration, your backend generates the token; a temporary Console token is useful for testing.

Service APIs have their own authentication requirements. For example, controlling a Voice Agent requires authentication for Conversational AI API requests. Follow the [Conversational AI authentication reference](/en/api-reference/api-ref/conversational-ai/authentication) when implementing that path.

Use the authentication guide for the service you are integrating. Do not assume that one token or one set of request headers can be reused across every Agora API.

## Client and backend responsibilities

| Part of your application | Typical responsibilities |
| --- | --- |
| **Client** | Present the UI, request microphone or camera access, connect with the appropriate SDK, and send or receive media and events. |
| **Backend** | Keep secret credentials, provide the authentication required by clients, and call service APIs for operations such as starting or stopping a Voice Agent. |

The Agent SDKs help your backend call Conversational AI services. RTC client SDKs connect users to live media. These are different roles within the same application.

## Product-specific concepts

Channel, stream, publish, subscribe, user role, and RTC connection describe how realtime media works. Read [Realtime Communication concepts](/en/realtime-media/rtc/core-concepts) when you need those details. RTC media channels and Signaling messaging channels are separate; consult the [Signaling concepts](/en/realtime-media/rtm/core-concepts) for messaging identities and channels.

A Voice Agent guide introduces the session concepts needed for its implementation. You can start with the [Voice Agent overview](/en/ai) and follow the relevant quickstart.
